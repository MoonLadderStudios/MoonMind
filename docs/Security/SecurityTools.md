# Security Tools and Assessment Workflows

This describes MoonMind's security program, including capabilities that still need qualification. The [passive repository scan](PassiveRepoScan.md), repository scanner adapters, image and SBOM jobs, web and API assessment jobs, and Trivy feed snapshots below have implemented job/report paths.

## Purpose and ownership

MoonMind helps its operator investigate and improve the security of source code, dependencies, build systems, container images, cloud resources, and running applications. An assessment explains what it examined, what it could not examine, the evidence behind each finding, and what verification supports a proposed fix. Direct review, threat modeling, and business-logic analysis are useful even when a scanner reports nothing.

The existing Omnigent agent remains responsible for reasoning. Its selected harness and Provider Profile apply to security work just as they do to other tasks. Security utilities run on demand in separate containers; they do not require a second model provider, a new agent backend, or scanner installations in the Omnigent host.

| Responsibility | Owner |
| --- | --- |
| Assessment procedure, investigation, and remediation reasoning | Portable [Skills](../Steps/SkillSystem.md) executed by the existing agent |
| Durable steps, dependencies, budgets, retries, and cancellation | Existing Temporal workflow and execution owners |
| Admitted input, workload, credential, and network authority | Existing trusted admission, Container Job, Secrets, and restricted-egress boundaries |
| Tool execution, resource limits, logs, outputs, and cleanup | Existing [Container Jobs](../ManagedAgents/DockerBackendService.md) |
| Evidence retention and operator presentation | Existing [report artifacts](../Artifacts/ReportArtifacts.md) and [artifact presentation](../Artifacts/ArtifactPresentationContract.md) |

Adapters translate a tool's invocation and results into those interfaces. Scanner-specific interpretation belongs in adapters and Skills, rather than branches in generic Temporal orchestration. Deterministic scanner jobs do not acquire model capacity. Completed work survives a retry of an interrupted step; a new attempt consumes the existing logical step's budget.

### Repository scanner jobs

`moonmind container repository-scan --admission scan.json` submits exactly one Gitleaks, Opengrep, or Trivy job through the existing Container Job transport. For example, an explicit Gitleaks admission is:

```json
{"scanner":"gitleaks","inputPath":".","outputDirectory":"artifacts/gitleaks-run","maxFiles":4096,"maxInputBytes":134217728,"maxReportBytes":8388608,"timeoutSeconds":300}
```

`outputDirectory` names the report directory inside the job's own output location, never inside the source. Compose registers the `repository-security` alias (the `--image-source` default) for API and worker as `ghcr.io/moonladderstudios/repository-security:latest` with pull policy `always`; `MOONMIND_REPOSITORY_SECURITY_IMAGE`, `MOONMIND_REPOSITORY_SECURITY_IMAGE_PULL_POLICY`, and `MOONMIND_REPOSITORY_SECURITY_REGISTRY_CREDENTIAL_REF` override it, and an explicit `MOONMIND_CONTAINER_BACKEND_IMAGE_SOURCES` list replaces all defaults. `--image` selects an explicit image containing the scanner, Git, Python, and installed runner. The adapter does not fetch rules or databases; feed snapshots come from the separate refresh job below.

The typed `repositoryScan` request travels with the existing job spec. Admission and the worker enforce its invocation, its single captured source input (`/inputs/source`, with Git metadata only for Gitleaks), a read-only root filesystem whose only writable paths are the job-owned output location and `/tmp`, no network, output declarations, cache access, and timeout. The image uses UID/GID `1000:1000`, matching the Compose worker that creates job storage. The runner uses a bounded private copy, omits output storage and admitted `exclusions`, ignores repository configuration and ignore files, and disables inline suppressions unless `allowInlineSuppressions` was explicitly admitted. It never edits source inputs, and entries the capture omitted remain coverage limitations. Gitleaks performs separate available-history and directory scans with full redaction; its evidence records refs, shallow/missing history, and available untracked files. Exclusions also apply to Git history pathspecs.

Opengrep requires `rules` entries containing `id`, an image-owned `path` under `/opt/moonmind-scanner-rules/`, `sha256`, and `license`. The base image ships no external rule corpus; include selected licensed rules in an operator-chosen derived image. Gitleaks may select one such trusted configuration; otherwise it uses built-in rules through a private configuration. Rule bytes must match their admitted identities. Remote and repository-local rule paths are rejected. Trivy explicitly selects `trivyScanners` (default `vuln,misconfig`); adding `secret` requires `gitleaksOwnsSecrets: false`. Vulnerability scanning requires a read-only `databaseCacheRef` and a `databaseDigest` naming one published feed snapshot. Trivy runs with every database, Java index, check and version update disabled, no repository config or ignore files, and `networkMode: none`.

#### Trivy feed snapshots

`moonmind container feed-refresh --admission refresh.json` submits one source-free refresh job, for example `{"feedCacheRef":"scanner-feeds","egressPolicyRef":"scanner-feeds","components":["vulnerability","checks"],"maxAgeHours":72}`. It declares an empty `inputAttachments` list, so no workspace is mounted, and carries no environment or credentials. Upstreams are fixed in code: `ghcr.io/aquasecurity/trivy-db:2`, and, only when selected, `trivy-java-db:1` and `trivy-checks:1`. Admission and the worker accept only an egress policy whose destinations are HTTPS 443 to `ghcr.io` and its blob host `pkg-containers.githubusercontent.com`. Trivy downloads the databases with its database-only flags. The checks bundle has no such flag, so a configuration scan of an empty directory refreshes it. Because Trivy silently falls back to embedded checks when that download fails, the refresh checks that the bundle is actually present. For air-gapped deployments, `"acquisition":"import","archiveArtifactRef":"art_..."` validates a tar archive of a Trivy cache directory without network access. Extraction accepts only regular files and directories under the component directories. It rejects absolute or `..` paths, links, devices, duplicate members, and anything over the size or entry bound; directories, including implied parents, count as entries.

The refresh job mounts the deployment's feed volume writable at `/opt/moonmind-scanner-feeds`. Scanner jobs mount the same named volume read-only at `/opt/moonmind-scanner-db` through a second cache source. Work is staged under `staging/`, then validated: component layout, metadata schema (vulnerability DB version 2, Java DB version 1), required files, and no links. The validated tree is published as `snapshots/<id>/` by one atomic rename, and `current.json` is replaced atomically. `<id>` is SHA-256 of sorted compact JSON pairs `[relative_path, file_sha256]`; it is the scan's `databaseDigest`. The manifest records each component's upstream (or source artifact), schema, content digest, retrieval time, upstream `UpdatedAt`/`NextUpdate` or checks bundle digest, and validation outcome. Readers address one identity, never see staging, and take no lock; concurrent refresh writers serialize publication and retention with a lock file on the volume. Retention keeps the current snapshot and two others. It renames old snapshots away before deleting them, so a racing reader sees absence, never a partial tree.

A scanner copies its snapshot into private writable cache space, verifies the copy against the identity, and records the snapshot in `execution.feed`. Freshness is the operator's `feedMaxAgeHours` (refresh: `maxAgeHours`, default 72), measured from the upstream `UpdatedAt` rather than from acquisition time, and is independent of image maintenance. The checks bundle has no `UpdatedAt`, so its age is its recorded `DownloadedAt`, which publication requires. Stale data still scans but limits coverage (`feed_snapshot_stale`). Absent, partially published, corrupt, or incompatible snapshots stop the scan with that limitation. Vulnerability scans of Java archives without the Java index report `java_db_unavailable`. `execution.feed.checks` distinguishes refreshed `snapshot` checks from Trivy's `embedded` fallback. A failed refresh publishes nothing; `refresh.json` names the prior snapshot it fell back to and whether that snapshot is still within policy and holds every requested component (otherwise `missingComponents` and `feed_components_missing`), or reports `feed_snapshot_unavailable`.

The existing artifact manifest retains sanitized native JSON and a `repository-scanner/v1` summary. Console content is withheld because arbitrary scanner diagnostics can contain source or secret metadata. Sanitization covers native records, execution inventories, and admission metadata before publication; sensitive paths use stable redacted identities. Missing, invalid, oversized, or unsanitizable native output leaves the secret inventory uncertain, so the summary withholds admission metadata (`admission: null`) and execution file lists, and manifest paths use opaque identities. Independently sanitized sibling evidence remains available. Recorded operation outcomes survive an aggregate job failure, which is disclosed separately as a limitation. Findings, execution, coverage, and verification remain separate: malformed records, parser errors, unsupported inputs, missing reports, timeouts, cancellation, and sanitization failures remain incomplete even when useful findings survive.

Pass summary artifact refs to `security.assess` using its existing `retained-report` tool and explicit file scope. The consumer authorizes native refs and publishes through the existing report bundle without an LLM. Opengrep coverage follows native examined paths, excluding skipped and parser-failed inputs; Trivy requires target and analysis evidence. Admission must match scope exclusions and suppression exceptions; withheld admission permits only partial coverage. Complete scans cover configured rules even without positive findings; comparison identity includes scanner version and effective configuration, excluding report destinations. Combined findings are deduplicated and capped at 4096 with explicit partial coverage; native evidence remains retained. Comparisons retain prior findings outside examined scope. Comparable absence does not verify a fix.

#### Image, archive and SBOM jobs

`moonmind container image-assessment --admission image.json` submits one typed `imageAssessment` job, separate from `repositoryScan` so target-image coverage is requested and reported apart from source scanning. `operation` is `assess` (target `registry` or `archive`), `sbom-generate` (`registry`, `archive`, or `source`), or `sbom-reassess` (`sbom`). For example, `{"operation":"assess","target":"registry","imageReference":"registry.example.com/team/app:stable","platform":"linux/arm64","egressPolicyRef":"registry","databaseCacheRef":"scanner-db","databaseDigest":"<snapshot id>"}`. Matching requires a feed snapshot; generation reads none.

Trivy never consults a Docker, containerd, or Podman daemon: registry images use `--image-src remote`, archives (Docker save or OCI layout tar) use `--input`, and SBOMs (CycloneDX 1.2–1.7 or SPDX 2.2/2.3 JSON) use `trivy sbom`. Archives and SBOMs arrive as `inputArtifactRef` attachments with `networkMode: none`. Registry jobs need an egress policy whose destinations are all `registry-api` traffic and include the target registry. Admission and the worker reject any other mount, environment, network, or image. The scanner image is a deployment image source, so its pull authority stays separate from `targetCredentialRef`. That credential is authorized at admission by the same `MOONMIND_REGISTRY_CREDENTIAL_GRANTS` that govern private job images, matched against the target's registry, repository, tag/digest, and principal. The worker resolves it only under that decision and mounts it read-only as a Docker config in job-owned storage, never in argv, environment, the request, or evidence. It is removed when the container exits and on release. Output containing the credential is withheld (`credential_material_withheld`). Registry failures are classified from private stderr (`target_registry_auth_failed`, `target_registry_access_denied`, `target_not_found`, `target_platform_unavailable`) without retaining its text.

Evidence names the examined `subject`: a registry tag is recorded as requested and resolved to the manifest digest and OS/architecture Trivy used (`target_digest_unresolved`, `target_platform_unrecorded`, or `target_digest_mismatch` otherwise; digests describe evidence and are not compatibility gates). Archive, SBOM, and source subjects carry the digest of the captured bytes. Generated CycloneDX SBOMs are retained unmodified as the `sbom` output, and the `image-assessment/v1` summary records their artifact ref, digest, generator and version, package count, and packages without identifiers. The operating-system component and identifier-less applications that only group packages are context, not packages. Reassessing a retained SBOM against a newer snapshot reads only the SBOM. Malformed, unsupported, empty, or self-declared incomplete SBOMs and packages without identifiers are explicit limitations. Embedded signatures or attestation claims are recorded as unverified provenance, never as trusted attestation. `security.assess` accepts assess and reassess summaries as `image` coverage over the subject asset; each summary states that matching covers only the inventory and does not establish exploitability, malware absence, or runtime safety.

#### Web and API assessment jobs

A typed `webAssessment` job runs the `web-assessment` image source (Compose default `ghcr.io/zaproxy/zaproxy:stable`, override `MOONMIND_WEB_ASSESSMENT_IMAGE`) against one `origin`. The worker renders its Automation Framework plan from the admitted routes, methods, exclusions, identity, `apiDefinition`, `discovery`, and limits, and writes it to the job's outputs. `baseline` crawls without posting forms, `api` imports the definition, and both check only passively. Only `active` runs the active scanner, at exactly `activeStrength`, after the passive reports are written, so those survive a timeout or cancellation.

Web jobs need an admitted scope: the mode's action class (`web-passive`, `web-api`, `web-active`), an egress policy limited to `live-target` destinations including the origin, and a `webOrigin` target whose `webRoutes` cover every route and method and whose `webExclusions` the job repeats. An identity's `credentialRef` needs an `application_auth` grant for the identity name and `web-assessment`. ZAP reads it from a read-only file, so it is never in the plan or argv. Form logins are verified on the verification route against an anonymous request; bearer tokens go on every request, so they have no anonymous comparison. The worker rejects definitions naming unadmitted servers, paths, or methods before ZAP imports them.

Collection redacts credentials, cookies, and login bodies from the native report and HAR. It publishes them with the plan and a `web-assessment/v1` summary, whose findings carry route, method, identity, rule, phase, bounded excerpts, and a reproduction reference. Coverage lists tested, untested, unreachable, and inaccessible routes, denied requests and redirects, and the authentication outcome. ZAP exit codes 1 and 2 are plan errors and warnings; any other code is a job failure. Plan errors or warnings, an early ZAP stop, failures, missing output, unverified authentication, and unreachable or untested routes make the result `partial`. `security.assess` reads the summary through `retained-report` as `web` coverage of the origin. Alerts never change the target or publish anything.

## Packaging and recommended tools

The recommended default is a small MoonMind-maintained repository-security image containing **Opengrep, Gitleaks, Trivy, Git, CA certificates, and only the helper runtime needed to invoke tools and prepare reports**. The same image can serve independent jobs with separate inputs, limits, results, and retries. A single invocation does not have to run every installed tool.

Cloud and application scanners use their maintained upstream images. Their larger Python, Java, and browser dependencies remain outside the repository toolbox and the Omnigent host. The image is a collection of executable utilities; it contains no agent loop or model credentials. Container execution goes through MoonMind's job service, without exposing a Docker socket, nested Docker, host networking, or privileged mode to the agent or scanner.

## Assessment authority and execution

An assessment starts from an admitted objective, target set, permitted operations, and limits. It can concern a repository snapshot, Git history, an image or SBOM, identified cloud accounts and regions, or application origins and routes. Scope also includes exclusions, credential references, permitted source/configuration inputs, output destinations, network access, and resource, request, and time budgets where applicable.

Skills can compose and adapt procedures within that authority. A prompt, scanner image, fixed entrypoint, or CLI convenience command is not an enforcement boundary; the trusted service and worker are.

### Workload profiles and admitted scope

A deployment declares approved invocations in `MOONMIND_CONTAINER_BACKEND_WORKLOAD_PROFILES`, a JSON array of profiles. Each profile binds an image source alias, an entrypoint, invocation modes (an `actionClass` plus an argv template), typed arguments (`string` with a required pattern, bounded `integer`, `enum`, or `input` naming a captured attachment path), fixed environment, credential slots, read-only rule/data caches, network mode and egress policy, declared outputs, and CPU/memory/timeout ceilings. Settings refuse a profile that names an undeclared image source or a writable cache, or uses bridge networking without an egress policy. An argv entry that references an omitted optional argument is dropped, so one mode admits approved variations instead of a frozen command each. Values replace placeholders inside argv entries and never pass through a shell.

A job selects `workloadProfile: {profileRef, mode, arguments, configurationExceptions, credentials}` with captured `inputAttachments` and resources; it never supplies the image, entrypoint, argv, environment, caches, workdir, network, or outputs. Admission renders the profile into the persisted spec. The worker renders it again at container creation and refuses content that differs, including after a profile edit or removal, rather than launching the old content or choosing another profile. Retries and exact replays pass the same checks.

Repository rules, plugins, ignore files, inline suppressions, and environment overrides are effective configuration. The deployment disables them in each mode's argv and fixed environment, and caller environment is refused. A request can name only a `configurationException` the profile defines as fixed argv text. The persisted spec records it, so it cannot select another mode, target, or credential.

The run's `assessmentScope` parameter is the operator's admission: `assessmentRef`, `profileRefs`, `actionClasses`, `targets` (workspace paths, artifact refs, or web origins with routes), `exclusions`, `configurationExceptions`, `networkRefs` (egress policies), `grants` (workload credentials), `maxJobs`, `maxJobSeconds`, and `evidenceIntent`. The operator submits it as `payload.assessmentScope` on a task-shaped `POST /api/executions` (or `initialParameters.assessmentScope`), and a malformed scope is rejected before any execution or schedule exists. Workflow and fan-out callers cannot set it. The run workflow copies it only into trusted step policy. Each launch boundary signs it into the session's container-job capability, and a malformed scope fails the launch. Step inputs, Skills, repository text, and model output cannot set or widen it. Child runs do not inherit the scope, so a scoped step gets no execution fan-out capability, and a step that requires fan-out fails at launch.

A scoped session's CLI, MCP, and replayed submissions must be profile or web assessment jobs inside that scope. Generic image/entrypoint jobs, repository-scanner jobs, other assessments' refs, unadmitted profiles, action classes, exceptions, or networks are refused before any job record exists. So are inputs outside the targets and inputs at, inside, or containing an exclusion (a capture cannot omit a subtree). Scoped jobs cannot select pull credentials. `maxJobs` counts the owner's jobs for the assessment, and exact replays consume nothing. Unscoped sessions cannot claim an `assessmentRef`. Older verifiers reject scoped capabilities rather than ignore the scope.

Tool configuration is part of the evidence: record effective rules, exclusions, ignore files, allowlists, severities, scanners, and environment options. Source, imported alerts, web pages, and scanner output are untrusted data; embedded instructions do not become workflow authority.

### Inputs, outputs, and caches

Container Job `inputAttachments` capture source snapshots and supplied artifacts once and mount them read-only, so later working-copy edits and retries cannot change what a job examines. Reports and temporary working data use separate, job-owned writable locations. Inputs are logical references owned by the existing workspace and artifact systems, never host paths or mounts. Output collection rejects traversal and symlink escapes. Native reports remain accessible through retained artifact references after the container is removed.

An agent authorized to edit code does so through the normal working-copy path, while the scanner examines an identified snapshot so results stay attributable.

A bounded, source-free refresh job obtains approved databases, rules, and templates without repository contents or assessment credentials. Scanners read an admitted read-only snapshot, so an untrusted scan cannot poison data later assessments use.

Record data source, resolved identity, acquisition and upstream update times, required components, and whether freshness was met. Missing or stale required data is reported as a coverage limitation or failure, never silently replaced by a clean result. Offline behavior covers every enabled component and remote dependency lookup, rather than only a single database-update switch; see [Trivy's air-gap guidance](https://trivy.dev/docs/latest/advanced/air-gap/). Feed refresh does not require rebuilding the tool image or introducing a permanent feed service.

### Credentials and networking

Workload credentials use the existing [Secrets System](SecretsSystem.md). A profile slot declares a `purpose` (`cloud_inventory` or `application_auth`), `env` or `file` delivery, and an issuer. A request names `{slot, credentialRef, account}`. Admission accepts it only if a scope grant `{ref, purpose, account, profileRefs, expiresAt, revision}` covers the job budget, and binds a value-free decision to that job, principal, assessment, and profile. An exact replay of admitted work is checked as of its admission, so a shortened or expired grant still returns the existing job; new jobs and start-failure restarts need a grant covering a fresh budget. The worker rechecks the decision and resolves the secret at the granted revision, so adoption by another job, rotation, revocation, and expiry fail closed (`credential_unresolved`, `credential_expired`). Values reach the container as read-only files under `/run/moonmind-credentials` or a worker-only `--env-file`, never argv. Docker keeps environment values in container configuration, readable by daemon administrators until removal, so prefer files. For cloud grants the worker exchanges the stored key for an STS session in the granted role, limited by read-only session policies (active access is not grantable), and renews it within the grant and budget only when it would expire before the budget ends; when the grant is too close to its end for another session, the current one serves until it expires. Issuance is recorded first, so a lost answer is counted and left to expire; failures keep the provider code (`credential_issuance_failed`). Every value delivered to the job, including sessions replaced by renewal or a restart, is redacted from logs and outputs, also on publication retries. Values leave the job's mount at container exit, stay worker-only for that redaction, and are deleted at cleanup; the stored credential is never rotated or deleted.

Model credentials, source-repository credentials, scanner-image pull credentials, private target-image credentials, cloud assessment credentials, and application authentication are distinct uses. Possession of one does not authorize another. Cloud identity and resource permissions enforce account/resource scope as well as the network policy; access to a cloud API hostname alone cannot confine a scan to an account.

Passive source analysis runs with `networkMode: none`, using prepared rule/data snapshots. Feed refresh, image acquisition, cloud APIs, and live-target assessment receive only their admitted destinations through the existing [restricted-egress owner](RestrictedEgress.md). Docker bridge mode alone is insufficient. Target enforcement addresses DNS resolution, redirects, alternate routes, private destinations, and control-plane/metadata access. Internal applications may be admitted explicitly without opening unrelated private networks.

Unsupported providers, expired credentials, denied API calls, skipped regions, and absent services remain visible in coverage. Prowler cloud results use native JSON-OCSF.

A passive web baseline still sends crawl requests, so it needs authorized target access like active testing ([web and API assessment jobs](#web-and-api-assessment-jobs)).

Scanner jobs are bounded CLI executions; a persistent cross-turn browser or proxy endpoint is a separate capability added only for a concrete need.

## Evidence, findings, and remediation

Each assessment retains a compact summary and sanitized native structured evidence through existing artifacts and report links. Use SARIF, JSON-OCSF, CycloneDX, or SPDX where the selected tool actually supports the relevant workload; no single export format is assumed for every scanner. A small versioned assessment summary references tool-native records instead of creating a universal vulnerability database.

The summary separates four questions:

- **Execution:** did each requested operation run, terminate, and publish usable evidence? Tool-specific finding exit codes are different from crashes or failed invocation.
- **Coverage:** which inputs, languages, dependencies, cloud resources, routes, rules, and data snapshots were examined, skipped, unavailable, or incomplete?
- **Findings:** what did the tool or agent observe, with native identifiers, locations, evidence, confidence, and contextual priority?
- **Verification:** which hypotheses or fixes were checked, against what revision or resource state, and with what result?

A successful process can report findings and incomplete coverage together. Missing or truncated reports, unknown schemas, denied reads, stale feeds, unsupported inputs, and timeouts never become empty findings or a secure verdict. The human-readable report remains useful without an LLM and identifies unperformed checks as Unverified with the reason and a feasible next verification step.

Sanitization occurs before output reaches ordinary persisted logs, model-visible evidence, or published reports. Gitleaks uses explicit full redaction. Native tool masking is useful but does not cover all surrounding source, request headers, cookies, environment data, or error text. Exercise every retained output path with synthetic secret markers. If sanitization or bounded parsing fails, retain safe diagnostics and report incomplete evidence instead of publishing the unsafe content. Native evidence means the native format with required sanitization, not unrestricted raw secret capture.

Agent-created findings cite their source or runtime evidence and distinguish a hypothesis from a reproduced defect. An agent's cross-file conclusion rests on cited code, configuration, tests, or observed behavior, never on a scanner that did not perform that analysis.

Prioritization uses exposure, asset importance, affected execution paths, exploit prerequisites, compensating controls, and available fixes. [CISA KEV](https://www.cisa.gov/known-exploited-vulnerabilities-catalog) and [FIRST EPSS](https://www.first.org/epss/) can enrich known-vulnerability triage; they do not replace local impact and applicability evidence. Record exclusions, accepted risk, and their reason and review/expiry conditions without erasing the underlying finding.

Remediation and publication follow the operator's admitted request. An assessment-only task does not permit source edits or cloud changes, and a task authorized to fix, test, and publish needs no further approval per step. Cloud auto-fix is an explicit operation, never a side effect of posture scanning.

Retesting links before/after inputs, findings, configuration, coverage, and relevant regression checks. A finding disappearing is not sufficient evidence of a fix if a file, route, rule, account, or feed disappeared too. Reports distinguish verified remediation from no-longer-observed findings, suppressed results, and unverified changes.

## Composable workflows

Skills compose these procedures through MoonMind's existing workflow, tool, artifact, and scheduling interfaces.

| Workflow | Composition and result |
| --- | --- |
| Repository assessment | Identify assets and trust boundaries; run applicable source, secret, dependency, and IaC checks as bounded jobs; perform targeted agent review; produce evidence, coverage, and prioritized recommendations. |
| Image and supply-chain assessment | Inspect an admitted image, supported image archive or OCI layout, or existing SBOM without a Docker socket; retain the actual image/inventory identity and generate an SBOM when requested; assess vulnerabilities and configuration with stated coverage. |
| Cloud assessment | Select provider/accounts/regions/checks; run Prowler with scoped credentials; explain permission and resource gaps; relate findings to IaC or code when evidence supports the connection. |
| Web/API assessment | Admit origin, routes, mode, and identity; run one `webAssessment` job per identity; investigate selected findings from its retained route, identity, and coverage evidence. |
| Investigate and repair | Combine scanner or imported findings with direct review, produce an authorized fix, run focused regression/retest work, and publish through the normal delivery path when requested. |
| Recurring review and advisory response | Reuse existing schedules and saved Skill definitions; reassess retained authorized inputs or SBOMs with refreshed data; compare compatible evidence and explain scope or coverage changes. |

GitHub ingestion (the `github-alerts` tool of `security.assess`, described in the [passive scan document](PassiveRepoScan.md#imported-github-alerts)) preserves upstream alert IDs, scanner/source identity, repository and revision scope, timestamps, and source links. Permission-denied, rate-limited, unavailable, and disabled products are explicit coverage states. Repeated imports are identifiable as the same upstream observation. Secret-alert payloads receive the same sanitization boundary as local secret findings.

Comparisons use retained assessment artifacts and explicit baseline references. They distinguish new, unchanged, resolved, accepted, and no-longer-observed findings without a new findings service, scheduler, dashboard, or tenant model. Updated feeds can change a vulnerability result even when source is unchanged; record that cause rather than attributing every difference to a code change.

## Maintenance and qualification

Repository maintainers own `.github/workflows/docker-publish-repository-security.yml`, which rebuilds current stable releases and the Python/glibc base weekly and on relevant main-branch changes; pull requests qualify both native architectures without publishing. Dispatch it for an immediate rebuild; optional `opengrep_version`, `gitleaks_version`, `trivy_version`, and `base_image` inputs select explicit releases and a compatible base. No tool-version equality gate constrains later updates or operator image choices.

Acquisition requires Opengrep's Cosign signature/certificate, Trivy's Sigstore bundle or legacy signature/certificate, and Gitleaks's HTTPS release checksums (Gitleaks publishes no release signatures). Release metadata falls back to anonymous access if GitHub refuses the optional CI token; failures report the upstream URL, status, and a redacted diagnostic. Missing assets or verification material, verification errors, or failed qualification stop publication. Each native build checks versions, findings and clean runs, the admitted runner, read-only permissions, offline Trivy data, SPDX SBOM generation, and isolated update promotion. One manifest update promotes `latest` only after both architectures pass, so failed runs leave the working default unchanged. Fixture failures log a bounded excerpt and retain full output as evidence.

The image exposes `/usr/local/share/repository-security/inventory.json` and adjacent `notices/`. Its job-owned `/tmp` stays executable because the official Opengrep release extracts a child executable there. Actions retains each architecture's tool assets/signatures, corresponding Opengrep source, inventory/base identity, image digest, SBOM, and qualification evidence for 90 days. Scanner updates use this workflow without rebuilding the Omnigent host, whose baked MoonMind CLI follows the host deployment lifecycle.

Qualification exercises the actual admitted Skill/tool-to-job-to-artifact/report journey with known vulnerable, repaired, and clean fixtures. Relevant cases include history versus worktree coverage, unsupported inputs, configuration overrides, missing/stale feeds, denied credentials/network targets, secret redaction, malformed reports, cancellation, cleanup, and resuming after one scanner has already completed. Cloud/API transports and local applications provide deterministic fixtures without mandatory paid providers or live production accounts. Optional external qualification is recorded as Unverified when unavailable; observed defects remain blocking.

Measure useful coverage and investigation quality, including findings from direct review that scanners miss, rather than detection percentages or broad benchmarks. Add tools when their demonstrated benefit warrants their maintenance cost.
